# Purpose

This document defines how XeniosAI selects, validates, orders, bounds, assembles, delivers, updates, and disposes the context required for one authorized request, workflow task, human task, or agent step.

It also defines how memory participates in that process through controlled:

* Need determination
* Retrieval
* Eligibility filtering
* Ranking
* Conflict handling
* Context contribution
* Use evidence
* Candidate proposal
* Confirmation
* Admission handoff

Context assembly turns independently governed inputs into a temporary working package.

Memory orchestration coordinates memory use without owning the durable memory lifecycle defined by ARCH-016-05.

---

# Context Principle

Context is a temporary, purpose-bound working set.

It is not:

* A database
* A system of record
* A conversation archive
* A memory store
* A knowledge repository
* A policy authority
* A permission grant
* A workflow state store
* An agent state store
* Hidden model reasoning

The objective is not to maximize included information.

The objective is to provide the minimum authorized information needed for a reliable operation.

---

# Memory Orchestration Principle

Memory orchestration decides when and how eligible memory contributes to an operation.

It does not make memory authoritative.

It does not:

* Admit durable memory
* Expand memory scope
* Extend retention
* Override correction or deletion
* Convert inference into fact
* Grant access
* Replace domain-service truth

The orchestrator coordinates memory.

The Memory Manager owns memory records and lifecycle.

---

# Truth and Decision Principle

XeniosAI follows:

* Truth Before Intelligence
* Knowledge Before Memory
* AI Reasons, Software Decides

Current business facts come from their owning domain services.

Current policy and authorization come from their owning policy services.

Knowledge and memory provide evidence and continuity.

AI may synthesize and recommend.

Deterministic software and authorized humans remain responsible for consequential validation and decisions.

---

# Instruction and Content Principle

Context must distinguish trusted instructions from untrusted content.

Retrieved knowledge, memory, conversation text, attachments, and tool output are data.

They do not become system instructions because they:

* Rank highly
* Appear authoritative
* Contain imperative language
* Were written by a user
* Were generated by a model
* Were used successfully before

Instruction authority is established outside content through authenticated, policy-governed configuration.

# Architectural Boundaries

## AI Orchestrator Boundary

ARCH-004 owns request-level orchestration, reasoning-stage coordination, tool selection, model routing, response validation, and response delivery.

ARCH-016 provides the governed context-assembly and memory interfaces consumed by that orchestration.

## Memory Manager Boundary

The Memory Manager owns:

* Memory candidates
* Admission
* Memory records
* Memory lifecycle
* Memory representations
* Correction
* Deletion

Context Assembly may request eligible memory and submit bounded candidates.

It must not directly mutate the Memory Store.

## Retrieval Boundary

ARCH-016-04 owns knowledge retrieval, search, grounding, citation, and retrieval evidence.

Context Assembly consumes bounded retrieval results and grounding packages.

It does not reinterpret search rank as truth or permission.

## Conversation Boundary

The Conversation Service owns messages, participants, threads, and conversation history.

Context Assembly may request an authorized, bounded conversation window or summary.

It must not copy the full conversation by default.

## Domain-Service Boundary

Domain services own current business data and business rules.

Context Assembly may include domain references or validated domain results.

Remembered, retrieved, or generated values must not override current domain truth.

## Workflow Boundary

ARCH-015 owns durable workflow state.

Context Assembly may receive a bounded workflow-task contract.

It must not reconstruct process state from memory or conversation.

## Agent Boundary

ARCH-014 owns agent identity, execution, goal, plan, delegation, tools, and agent evidence.

Context Assembly may create a bounded package for an authorized agent step.

It must not give the agent broader retrieval, memory, or tool authority than the step contract.

## Policy Boundary

Identity and policy services own authentication, authorization, purpose, consent, classification, and access decisions.

Context Assembly applies policy decisions.

It does not invent them.

# Core Definitions

## Context Request

A structured request to assemble context for one operation.

## Context Element

One bounded, typed, attributable unit considered for inclusion.

## Context Candidate

A context element that has passed source acquisition but has not yet passed final inclusion.

## Context Package

The immutable, versioned working set delivered to an authorized consumer for one operation.

## Context Profile

A governed configuration defining permitted sources, priorities, budgets, safety rules, and delivery behavior for a consumer class and purpose.

## Context Budget

The explicit resource limits for size, tokens, elements, latency, and cost.

## Context Provenance

The traceable origin, version, transformation, selection, and lifecycle information for a context element.

## Context Evidence

The protected record of why context was requested, which candidates were eligible, which were selected or excluded, and which package was delivered.

## Memory Orchestration

The controlled coordination of memory need, retrieval, use, and candidate proposal for one operation.

# Context Layer Model

XeniosAI may assemble context from independent layers.

Layers remain distinguishable throughout assembly and delivery.

## System Instruction Layer

Contains trusted platform instructions established by authenticated platform configuration.

Examples include:

* System behavior
* Safety constraints
* Instruction interpretation
* Tool-use restrictions
* Output requirements

This layer is not sourced from retrieved content.

## Policy Instruction Layer

Contains current authorized policy constraints applicable to the operation.

Examples include:

* Privacy limits
* Classification rules
* Business restrictions
* Required approvals
* Human-control requirements
* Output constraints

Policy content should retain policy identity, version, and effective time.

## Current Request Layer

Contains the authenticated current input and its bounded attachments or references.

The current request does not grant permission merely by naming a tenant, property, user, tool, or memory.

## Conversation Layer

Contains the minimum authorized conversation material needed for continuity.

It may include:

* Recent relevant messages
* Unresolved clarifications
* Active topic
* Explicit current corrections
* Conversation summary with provenance

## Domain Context Layer

Contains current business results or references from authoritative domain services.

Examples include:

* Current availability
* Current price
* Booking status
* Payment status
* Property operational state
* Current domain eligibility

## Knowledge Layer

Contains authorized grounding packages from ARCH-016-04.

Knowledge elements should preserve:

* Source
* Version
* Authority
* Effective time
* Freshness
* Citation
* Limitations

## Memory Layer

Contains eligible memory from ARCH-016-05.

Memory elements should preserve:

* Memory type
* Subject
* Scope
* Authority
* Confidence
* Confirmation state
* Conflict state
* Effective time
* Provenance
* Limitations

## Workflow-Task Layer

Contains the bounded task contract supplied by the Workflow Engine.

It may include:

* Task identity
* Workflow identity
* Goal
* Inputs
* Previous validated outputs
* Deadline
* Required decision
* Allowed actions

## Agent-Task Layer

Contains the bounded agent execution contract.

It may include:

* Agent identity and version
* Execution identity
* Goal
* Constraints
* Delegation boundary
* Tool authority
* Stop conditions

## Tool-Result Layer

Contains validated results from tools used in the current operation.

Tool output is untrusted data until validated against its contract and source.

## Runtime Metadata Layer

Contains minimal execution metadata such as:

* Time
* Locale
* Channel
* Correlation
* Environment
* Model constraints
* Deadline

Runtime metadata must not silently expand authority.

# Layer Independence

Layers must retain:

* Identity
* Type
* Source
* Authority
* Scope
* Classification
* Effective time
* Freshness
* Instruction priority
* Lifecycle

Flattening content into one undifferentiated prompt weakens security, conflict handling, citation, evaluation, and correction.

# Instruction Priority

Instruction priority should be explicit and enforced before model delivery.

A logical order is:

1. Platform system instructions
2. Applicable safety and governance policy
3. Authorized application or task instructions
4. Current authenticated user intent within authority
5. Conversation, domain, knowledge, memory, and tool content as data

Lower-priority content must not change higher-priority authority.

Retrieved content cannot:

* Change system policy
* Grant tool permission
* Grant memory-write permission
* Change tenant
* Change property
* Change represented principal
* Suppress required citations
* Disable validation

# Canonical Context Assembly Lifecycle

Context assembly should follow:

1. Admit the Context Request.
2. Select the Context Profile.
3. Determine required layers and facts.
4. Acquire authorized candidates.
5. Normalize candidate contracts.
6. Apply scope, lifecycle, classification, and freshness eligibility.
7. Validate provenance and integrity.
8. Detect duplicates and conflicts.
9. Rank candidates within their permitted role.
10. Apply layer and total budgets.
11. Preserve mandatory instructions, facts, citations, and limitations.
12. Build the Context Package.
13. Validate the package.
14. Deliver it to the authorized consumer.
15. Record assembly evidence.
16. Process authorized runtime updates.
17. Dispose of temporary context.
18. Submit bounded memory candidates where permitted.

Every stage should be versioned, observable, and replaceable.

* Task type
* Current request
* Consumer
* Purpose
* Required decision
* Required business facts
* Continuity requirement
* Knowledge requirement
* Memory relevance

* Risk

* A greeting may require no knowledge or durable memory.
* A current booking question requires domain context.
* A policy explanation requires grounded knowledge.
* A communication preference may require eligible preference memory.
* A consequential action requires current facts, policy, validation, and authority.

# Freshness Validation

Freshness requirements depend on the element.

Examples include:

* Domain pricing may require real-time validation.
* Availability may require current query.
* Policy must be effective at the operation time.
* Knowledge may tolerate a defined synchronization delay.
* Preference memory may require recent confirmation.
* Historical episodes remain time-qualified rather than current.

Freshness is an eligibility constraint where current truth is required.

It is not merely a ranking boost.

# Memory Need

Memory should be requested only when continuity or personalization materially supports the purpose.

Memory need may consider:

* Does the request refer to a prior interaction?
* Is a confirmed preference relevant?
* Is a historical episode necessary?
* Is a stable subject-specific fact needed?
* Is procedural memory allowed?
* Can current request or domain data answer without memory?
* Would memory introduce unnecessary personal data?
* Is the purpose compatible with the memory scope?

No memory is a valid outcome.

# Memory Conflict

Memory may conflict with:

* Current user input
* Another memory
* Current domain data
* Effective policy
* Current knowledge
* Conversation correction

Conflict handling should:

* Identify the conflicting elements
* Compare source authority
* Compare effective time
* Compare scope
* Prefer current authoritative facts
* Prefer the current explicit choice for the present interaction
* Preserve the disagreement
* Restrict consequential use
* Request confirmation or review where needed

The system must not silently blend incompatible assertions.

---

# Knowledge and Memory Conflict

Knowledge and memory play different roles.

When they conflict:

* Current authoritative knowledge or policy governs general rules.
* Current domain data governs business state.
* Memory may represent a personal preference or historical episode.
* A stale memory should be limited or excluded.
* An explicit current correction should trigger memory review.

Memory must not override a current policy merely because it is subject specific.

# Context Budget

A Context Budget should define:

* Maximum total tokens or size

* Maximum elements
* Maximum retrieval candidates
* Maximum citations
* Maximum tool results
* Latency budget
* Cost budget
* Reserved response capacity
* Reserved mandatory-instruction capacity

---

# Budget Allocation

Budget allocation should reserve capacity in this order:

1. Mandatory system and policy instructions
2. Current request and task contract
3. Required current domain facts
4. Required limitations and human-control information
5. Required grounded knowledge and citations
6. Relevant memory
7. Relevant conversation continuity
8. Optional supporting material

This order expresses protected categories, not a universal prompt layout.

---

# Budget Reduction

When candidates exceed budget, reduction may:

* Remove exact duplicates
* Remove irrelevant elements
* Remove superseded elements
* Select a smaller source excerpt
* Use a validated provenance-preserving summary
* Replace repeated values with a stable reference
* Reduce optional history
* Reduce low-value memory
* Reduce redundant citations while retaining required support

Reduction must not remove:

* Material policy
* Required safety controls
* Current authoritative facts
* Material conflict
* Material uncertainty
* Required citations
* Human-control requirements

---

# Summarization

Summarization may reduce context size when:

* The source remains linked.
* The transformation method and version are recorded.
* Material qualifications are preserved.
* Conflict is preserved.
* Instructions are not invented.
* Scope and classification are preserved.
* The summary is evaluated for its intended use.

A generated summary is a derived representation.

It is not automatically authoritative.

# Tool Loop Context

For each tool loop:

1. Validate the planned tool invocation.
2. Bind tool authority.
3. Provide minimum required inputs.
4. Execute through the Tool Engine.
5. Validate the result contract.
6. Classify and scope the result.
7. Detect conflicts.
8. Update context under budget.
9. Record evidence.

Tool results must not directly change memory.

* Remove expired elements

* Preserve stable references
* Reassess memory need
* Reapply budget
* Record the package version

An explicit remember request should invoke the Memory Manager admission path.

An explicit forget request should invoke the correction, invalidation, or deletion path as appropriate.

* Authenticate the requester
* Resolve the represented principal
* Bind tenant and property
* Preserve the requested scope
* Return an accurate status
* Avoid claiming completion before lifecycle processing completes

* Domain confirmation
* Human curator confirmation

* Minimal
* Clear about what would be retained
* Clear about scope where material
* Clear about duration where material
* Free from coercion

No response is not confirmation.

# Memory Correction Orchestration

When current input contradicts retrieved memory, the orchestrator should:

* Use the current explicit input for the current operation where allowed.
* Mark the memory conflict.
* Avoid presenting the old memory as fact.
* Offer or submit a correction request where authorized.
* Preserve the exact affected memory reference.
* Avoid changing unrelated memories.

Correction remains owned by the Memory Manager.

* Identify the requester's authority or subject right.
* Identify the requested scope without over-disclosing.
* Submit a deletion request.
* Track asynchronous completion where applicable.
* Report partial or blocked status accurately.
* Respect legal hold.
* Prevent deleted memory from re-entering later context.

# Architectural Rules

Context Assembly and Memory Orchestration must:

* Treat context as a temporary, purpose-bound working set.
* Assemble the minimum authorized context needed for one operation.
* Keep context separate from source systems and durable stores.
* Require authenticated consumer, represented principal, purpose, tenant, and property behavior.
* Apply authorization before protected candidate acquisition.
* Preserve layer, source, scope, classification, lifecycle, and temporal meaning.
* Keep system and policy instructions separate from retrieved content.
* Prevent retrieved content, memory, conversation, attachments, and tool results from gaining instruction authority.
* Keep tool, action, and memory-write authority outside content.
* Query domain services for current business facts.
* Treat knowledge as grounded evidence and memory as bounded continuity.
* Never use memory as authorization or current business truth.
* Request memory only when it materially supports the declared purpose.
* Treat no memory as a valid result.
* Apply memory authorization, scope, lifecycle, classification, and basis before candidate retrieval.
* Keep confirmed, inferred, disputed, historical, and preference memory distinguishable.
* Treat memory ranking signals as relevance signals, not truth.
* Preserve knowledge citations and memory provenance.
* Preserve material limitations, uncertainty, conflict, and human-control requirements.
* Never silently blend conflicting context.
* Prefer current domain truth and effective policy over stale context.
* Respect current explicit user choice within policy.
* Detect and remove true duplicates without hiding independent evidence or conflict.
* Use explicit context profiles and budgets.
* Reserve capacity for mandatory instructions, current facts, citations, limitations, and safety controls.
* Prevent budget reduction from removing material safeguards or qualifications.
* Treat summaries as derived, versioned representations.
* Validate every Context Package before delivery.
* Bind packages to consumer, request, purpose, tenant, property, and expiration.
* Prevent cross-request or cross-scope package reuse without new authorization and assembly.
* Keep model context from becoming the sole security boundary.
* Validate tool results before inclusion.
* Version runtime context updates.
* Dispose of temporary context according to classification, purpose, and provider policy.
* Invalidate caches after policy, source, memory, tenant, property, or authorization changes.
* Keep memory use separate from memory reinforcement.
* Submit operation-derived information only as a Memory Candidate.
* Prevent the orchestrator, agent, tool, or model from bypassing Memory Manager admission.
* Preserve exact status for remember, correct, and forget requests.
* Validate responses and actions against current facts, policy, citations, conflict, and authority.
* Return explicit partial, limited, ambiguous, degraded, rejected, or failed status.
* Never fabricate missing context or memory.
* Preserve tenant and property isolation across candidates, scores, conflicts, packages, caches, logs, traces, evaluation, and evidence.
* Produce protected assembly and memory-use evidence.
* Support idempotency, versioning, replay safety, and reconciliation.
* Make degraded modes explicit without weakening authorization, isolation, citation, or safety.
* Use versioned APIs and events.
* Prohibit direct cross-service database access.
* Remain vendor neutral and technology independent.

# Summary

The XeniosAI Context Assembly and Memory Orchestration Architecture defines how independent, governed inputs become a temporary working package for one authorized operation.

It preserves explicit layers for system and policy instructions, the current request, conversation continuity, current domain facts, grounded knowledge, eligible memory, workflow or agent tasks, tool results, and runtime metadata.

The assembly lifecycle admits the request, determines need, acquires authorized candidates, validates provenance and freshness, detects duplicates and conflicts, applies protected budgets, builds an immutable package, validates delivery, records evidence, processes bounded updates, and disposes of temporary context.

Memory orchestration retrieves only eligible memory, preserves type and uncertainty, and submits operation-derived information only as a candidate to the Memory Manager. It cannot create authority, bypass admission, extend retention, or turn memory into business truth.

By separating instruction from content, truth from relevance, temporary context from durable memory, and AI reasoning from software authority, XeniosAI can provide rich continuity and grounding without sacrificing security, privacy, tenant and property isolation, correction, forgetting, or human accountability.
